# 2026-09-10

## P2P 连接超时修复（area-network-communication）
- 现象：两台设备（192.168.0.x）P2P 收文件一直"连接超时"。最可能原因：浏览器 mDNS 候选（xxx.local）在路由器/AP 隔离下无法解析，ICE 直连建不起来。
- 修复：① RTCPeerConnection 加 STUN（stun.qq.com / stun.miwifi.com / google）辅助打洞；② P2P 15 秒连不上自动降级为服务器分块中转（relay-request/relay-chunk，256KB 块 + ack 回调流控，不落盘）；③ 目标离线时服务端也回 ack 防发送端卡死。
- 关键 bug：前端 relay-chunk handler 最初没回 ack，发送方流控卡死在第一块——测试脚本（双 socket.io-client + ack 模拟浏览器）抓出并修复。
- 中转通道三场景测试全过：分块按序到达、目标离线 ack、无多余重发。
- 清理：删除了旧版遗留的 uploads/ 目录（新版服务器零存储）。
- 最终定版（用户要求）：完全去掉中转降级，文件只走 P2P 设备直连；服务器仅做信令（最多帮忙建立连接）。保留 STUN 打洞；连不上直接报失败提示（含"请检查两台设备是否在同一网络"）。relay 相关代码已全部移除并验证无残留。
- 关键优化（用户提议"只走 192.168.0.x"）：mDNS 候选改写——服务器转发 signal 时附 fromIp，前端用正则把对端 SDP/ICE 候选里的 `uuid.local` 全部替换为对端真实局域网 IP（清洗 ::ffff: 前缀），强制 WebRTC 直奔真实 IP 连接，绕开 mDNS 解析失败问题。单测 + 双客户端信令测试通过。
- 环境线索：本机网卡有 198.18.0.1 utun 接口 = 代理/VPN TUN 模式（Clash/Surge 类）在跑，会劫持 WebRTC UDP，是 P2P 超时的另一可疑原因；建议用户测试时关代理。
