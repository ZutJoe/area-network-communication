# 2026-09-09

## 局域网通信工具改造（area-network-communication）
- 新增三个需求：① Cmd/Ctrl+V 粘贴图片直接发送；② 文件选择支持任意类型（移除 accept 限制）；③ 大文件传输（几百 MB～GB）。
- 大文件方案：放弃 base64 走 Socket.IO（原上限 100MB），改为 HTTP 流式上传 `POST /upload?name=`（req.pipe 写磁盘，不占内存）+ `GET /files/:id/:name` 下载/预览（支持 Range）。
- 前端 XHR 上传带进度条；上传完成后通过 socket 广播元数据（id/name/size/mime），发送端用 token 去重、把本地进度条替换为最终卡片。
- 新增拖拽发送；uploads/ 目录每小时清理超过 24h 的文件。
- 测试：300MB 文件上传 0.2s（localhost ~1.5GB/s），下载 SHA1 一致。
- 坑：端口 3000 常驻旧实例，改代码后需先 `lsof -ti tcp:3000 | xargs kill`。
- 追加需求（用户确认）：服务每次启动时清空 uploads/ 遗留文件（不跨会话保留）；前端点击文件先 HEAD 探测，404 则在聊天区提示"文件在服务端已被清理，请对方重新发送"；图片加载失败降级为失效提示卡片。
- 追加：图片点击放大预览（lightbox 全屏遮罩，带文件名/大小、下载按钮，点背景或 Esc 关闭）。纯前端改动，静态文件即时生效无需重启。
- 追加（用户选择）：文件传输改为 WebRTC P2P 直传——服务器只做信令转发（`signal` 事件 + message 附带 sid），文件走 DataChannel（256KB 分块 + bufferedAmount 背压控制），不落服务器磁盘；接收方点卡片发起 offer，流式接收组装 Blob，图片直接预览、文件点击保存。限制：需双方同时在线，发送方刷新/离线则分享失效。信令双向转发已用 socket.io-client 双客户端脚本自动化测试通过。
- 遗留：server.js 的 /upload、/files 中转端点保留但前端已不再调用；后台 node 进程会被沙箱回收，需留意重启。
- 注意：本机 curl 需 `--noproxy '*'`，否则被代理劫持返回 502。
- 修复：P2P 重写 index.html 时遗漏了 user-list 渲染 handler（数据格式已改为 [{id, ip}]），已补回。教训：整文件重写前先核对旧文件的事件处理清单。
- 追加（用户要求）：图片不走 P2P，恢复 HTTP 上传到服务器、所有人直接显示预览（可点大图）；非图片文件仍走 P2P。sendFiles 按 MIME 路由：image/* → uploadImage（XHR+进度条，广播 type:'file'），其余 → sendP2PFile（file-offer）。修复过程中 sendP2PFile 残留旧 forEach 闭合导致语法错误，node -e "new Function(js)" 内联脚本语法检查通过。
- 最终传输策略：图片=服务器中转（即时显示，24h/重启清理）；其他文件=P2P 直传（需双方在线）。
- 最终版（用户要求服务器零存储）：图片改为 base64 随 socket 消息直发（≤10MB，超限转 P2P），服务器只中转不落盘——已删除 /upload、/files 端点和 uploads 目录及清理逻辑；server.js 设 maxHttpBufferSize 25e6。5MB base64 图片广播实测通过。当前形态：文本+图片走消息通道，大文件走 WebRTC P2P，服务器无任何存储。
